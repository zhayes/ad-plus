# 推倒重来：A+B+商品库 的目标架构、质量上限与开源盘点

> 日期：2026-11-09
> 前提：不继承现有 `project = 当前版本 = 七阶段` 的模型，按「商品 → 多条能投的片子」重新设计。
> 结论先给：**架构值得重做，产品不值得全量重写；开源没有 Kickart 的克隆，但有一块可以直接租的 API 和几块可复用的组件。**

---

## 0. 三个问题的直接回答

| 问题 | 回答 |
|---|---|
| **可行性** | 重做**内核**高（8/10）；全量推倒重写对当前团队**低**（3/10，12–24 人月 + 内容供给）；绞杀式重构最高（9/10） |
| **质量能否对齐** | 分能力：**B 爆款裂变可以 1:1**（同一后端就是同一质量，甚至可直接调 Kickart API）；**A 模板成片不行**（缺模板/音乐供给，不是模型问题）；**商品保真可以反超** |
| **有没有开源版可抄** | **没有 Kickart 克隆**。但有 4 块可用件 + 1 个官方 API 封装：MoneyPrinterTurbo、OpenCut、NarratoAI、OpenTimelineIO、`volcengine/byted-kickart-skills` |

---

## 1. 如果重来，只保留一个原语：Timeline

现在的模型是「项目 → 阶段 → 版本 → 镜头」，状态由阶段派生，导致每加一种玩法（批量、裂变、精修）都要改阶段逻辑。

重来只留一个东西：**一条时间线**。

```
Timeline = 轨道(track) 的集合
  video    : 片段(clip) 序列，每段有源、入出点、变换
  overlay  : 商品板、字幕、贴纸、品牌元素
  audio    : 旁白、BGM、音效
```

- **一条片子 = 一次 timeline 渲染**；
- **一个变体 = 对 timeline 的一次 patch**（换文案/换色/换 BGM/换封面/换顺序）；
- **一个批次 = 一组 patch + 一次预算**；
- **精修 = 直接编辑 timeline**；
- **渲染 = 纯函数** `render(timeline, assets, renderer_version)`，可缓存、可复现、可回滚。

这一步做完，A/B/自由创作/商品库都只是 timeline 的不同入口，不再是四套流程。

## 2. 目标架构

```
┌─────────────────────────────────────────────────────────────┐
│ 入口层                                                        │
│  /create 一句话成片   /batch 批次   /fission 裂变   /studio 精修 │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ 编排层                                                        │
│  Planner（LLM，只产出 JSON）   Variant Engine（轴 → patch）    │
│  Policy（预算/能力/质量门）     Scheduler（队列/并发/重试）      │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ 领域层                                                        │
│  Timeline   Asset Graph   ProductTruth   Template Registry    │
│  Render（确定性合成）  Provider（生成式片段）  QA（自动检查）    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ 基础设施                                                      │
│  本地：FFmpeg / Remotion / ONNX / SQLite / 文件                 │
│  云端（可选）：模型 API、对象存储、分享链接、计费                 │
└─────────────────────────────────────────────────────────────┘
```

**分层规则（比现在的 OpenMontage 边界更硬）：**

1. Planner 不写代码，只产出 schema 校验过的 JSON；
2. Template 声明槽位，不写业务逻辑；
3. Render 是纯函数，不读全局状态；
4. Provider 只返回 clip + 元数据（prompt/seed/model/cost），不改 timeline；
5. QA 只读产物，打分 + 给原因，不做修复。

## 3. 数据模型（六个对象，够用）

```text
Product     商品真相：SKU、标题、类目、卖点(claims)、禁用词、原图、
            抠图板(plate)、标签 OCR、颜色/尺寸、授权状态
Persona     人设：授权记录、参考图集、voice_id、一致性 embedding
Template    模板：槽位定义、约束(时长/比例/安全区)、轨道结构、预览图、版本
Timeline    时间线：轨道 + 片段 + 叠加层 + 音频，可序列化为 OTIO 风格 JSON
Variant     变体：batch_id + axes + timeline_id + 成本 + 状态
Batch       批次：brief + axes + variants + policy(预算/并发/门禁)
Render      渲染：timeline_hash + renderer_version + 产物 + qa 报告
```

关键设计：

- **Product 是服务，不是一张表**。它负责「商品像素不变」：抠图、标签 OCR、合成回贴、SSIM 校验。这是 Ad+ 唯一能稳定赢 Kickart 的地方。
- **Template 是数据**。设计同学产出 JSON（槽位 + 约束 + 预览），不是 React 代码。否则模板供给会被工程瓶颈卡死——这正是现在 `local_motion` 的问题。
- **Variant 只存 patch**，不存整条 timeline。6 个变体共享 95% 的 timeline，改一处只重渲染受影响片段。

## 4. 生成链路

```
Brief ──► Planner ──► CreativePlan(hooks/claims/beats) ──► Template 填槽
                                                           │
                                    ┌──────────────────────┴──────────┐
                                    ▼                                 ▼
                            Timeline(确定性)                  Provider clips(生成式)
                                    │                                 │
                                    └────────► Render ◄───────────────┘
                                                  │
                                            QA（自动） ──► 人审（只审入围）
                                                  │
                                            Variant / Batch
```

- **确定性部分是默认**：字幕、商品板、版式、转场、封面——零成本、可复现、品牌安全。
- **生成式部分按需**：只给「需要真人/场景/口播」的片段付费，不整条重生成。
- **成本在时间线上可见**：每个 clip 带 `cost_usd`，批次累加即报价。

## 5. 商品库为什么是核心，而不是附属

电商广告的第一性要求不是「好看」，是「**收到的货和视频里一样**」。Kickart 的模板再漂亮，用户最怕的仍是「AI 把 SKU 画歪了」。

所以 ProductTruth 要做成独立服务：

| 能力 | 做法 | 价值 |
|---|---|---|
| 抠图板 | SAM2 / rembg，边缘羽化 + 阴影 | 商品可复用、可合成 |
| 标签保真 | OCR + 关键字段比对 + SSIM | 防「AI 改包装」 |
| 卖点约束 | claims 与证据绑定，禁用词过滤 | 过广告法/平台审核 |
| 合成回贴 | 生成画面里商品区域回贴原图 | 生成式也能保真 |
| 多规格 | 同 SKU 多角度/多色 | 一个商品出 N 条 |

这套东西 Kickart 不会替你做（它是平台视角，不是商家视角），也是「同模型下质量对齐」之外真正能形成差异的地方。

---

## 6. 质量能不能对齐

先把「质量」拆开，避免用一个词掩盖三种问题：

| 能力 | 同模型下能否对齐 | 关键条件 | 判断 |
|---|---|---|---|
| **B 爆款裂变** | **能，1:1** | 直接用同一后端/API；或 Seedance 2.5 reference-to-video + 商品解析 + 字幕擦除 | 质量继承源片，成本近零 |
| **A 模板成片** | **难**（4/5 封顶） | 8–16 套真模板 + 音乐库 + 字幕体系 + 6–9 个月供给 | 不是模型问题 |
| **商品保真** | **能反超** | 商品锁 + 标签 OCR + 合成回贴 | 差异点 |
| **数字人口播** | 能接近 | LatentSync(Apache-2.0) 或云 provider；别商用 Wav2Lip | 许可证风险 |

**为什么 B 能 1:1：** Kickart 的爆款裂变本身就是一个异步云任务——参考视频（5–60s、≥480p、MP4/MOV、≤50MB）+ 商品信息（抖店/抖音链接或商品 ID）+ 模特图 + 场景图 + 创意 prompt + 字幕/擦除/水印 + `template_id`，提交后轮询结果，失败码里连「商品信息获取失败」「参考视频时长错误」都列好了。它的质量 = 视频模型 + 这条流水线，没有魔法。

**为什么 A 难：** 一键成片的观感来自模板库、音乐、字幕、节奏，这些是设计供给，不是模型能力。同模型只能保证「单镜头不差」，保证不了「整条像广告」。

**结论：质量对齐的正确姿势是「买 B、建 A 的供给、做商品真相」，而不是「用同一个模型重写一遍」。**

## 7. 三条路线

| | 全量重写 | 绞杀式重构（推荐） | 直接集成 Kickart |
|---|---|---|---|
| 到 A+B 可用 | 6–9 个月 | 3 个月 | **2–4 周** |
| 质量 | 取决于供给 | 与现在持平，逐步提升 | B 完全对齐 |
| 控制力 | 最高 | 高 | 低（供应商/条款/额度） |
| 风险 | 高（现金流/团队） | 中 | 战略依赖 + 素材出机 |
| 适合 | 有 6–8 人团队 | 1–3 人 | 验证需求/过渡 |

**推荐组合：绞杀式重构内核 + B 先租后建。**

1. 把 Timeline / Asset / ProductTruth / Variant 四个包抽出来，作为新内核；
2. 现有 FastAPI + Tauri 外壳保留，`project_store` 变成适配器；
3. A 用新内核 + 模板渲染；B 先接 Kickart API 或 Seedance reference-to-video 验证需求；
4. 等量起来，再把 B 的供应商替换成自建，保留接口不变。

这也是唯一能避免「重写两年、上线时对手又领先两代」的路径。

| 模块 | 人月（粗估） | 说明 |
|---|---|---|
| Timeline + 渲染 + 缓存 | 6–8 | 最核心，决定后面一切 |
| Asset graph + ProductTruth | 4–6 | 抠图/OCR/合成/回贴 |
| Planner + Template registry | 4–5 | schema、填槽、预览 |

## 10. 许可证雷区（会直接影响能不能卖）

| 组件 | 问题 | 处理 |
|---|---|---|
| **Remotion** | ≤3 人免费；超过要 Company License；自动化产品 $0.01/次、$100/月起 | 现在就在用，商业化前必须核算 |
| **Wav2Lip** | 仓库**无 license**，README 明确仅研究/学术，商用禁止 | 换 LatentSync（Apache-2.0）或买云口型 |

| **模型输出** | 各家条款不同（商用/署名/禁止某些用途） | Provider 注册表里加 `license_scope` 字段 |

## 11. 什么情况下才值得全量重写

满足**三条以上**才考虑：

1. 现有阶段模型已经成为新功能的硬阻塞（每次加玩法都要改 `production.py`）；
2. 有 6 人以上、能并行 6 个月；
3. 已有稳定的模板/音乐供给（否则重写也只是换了个空壳）；
4. 明确要做云端多租户（本地优先的话，重写收益小很多）。

否则：**绞杀式重构**。先把 Timeline 和 ProductTruth 抽出来，UI 和外壳不动，三个月就能看到 A+B 的雏形。

---

## 12. 一页决策

- **架构**：Timeline-first + Asset graph + Variant engine + 两个渲染器。
- **质量**：B 买/接，A 靠模板供给，商品真相做差异。
- **开源**：没有克隆；用 OTIO 做 schema、OpenCut 做编辑器参考、Kickart skills 做 B 的契约、LatentSync 替 Wav2Lip。
- **路径**：绞杀式重构，3 个月出 A+B 雏形；B 先租后建。
- **别做**：全量重写、自己训模型、早期做云编辑器、早期做模板市场、自动发布（合规风险）。

## 13. 集成 Kickart API 的限制清单（追问补充）

先纠正一个容易误读的点：**Apache-2.0 只是 `byted-kickart-skills` 示例仓库的许可；真正干活的 `@volcengine/kickart-open-mcp` npm 包写的是 `SEE LICENSE IN LICENSE`（专有许可），服务本身是商业 API。** 能不能封装进你的产品，取决于那份 LICENSE 和火山引擎服务条款，不取决于 GitHub 上的 Apache-2.0。

### 13.1 六类限制

| 类别 | 具体限制 | 证据 | 对 Ad+ 的影响 |
|---|---|---|---|
| **许可/商务** | npm 包专有许可；转售、白标、竞品封装是否允许未知 | `package.json: "license": "SEE LICENSE IN LICENSE"` | 可能只能「用户自带账号」，不能做成你的后端 |
| **鉴权** | OAuth 设备授权，逐用户登录；refresh token 固定 30 天；token 存本机（keytar 或 `~/.kickart/hosts.json` 0600） | npm README + SKILL 前置校验 | 做不了无感多租户；每个用户都要有火山账号并授权 |
| **数据** | 本地素材自动上传到 KickArt 对象存储；任务完成后产物默认同步回 KickArt（`/openapi/ai_effect/media/save_url`） | npm README | 与「素材不出机」直接冲突；品牌客户 NDA 难过 |
| **发布** | `query_task_v2` **默认 `--auto-publish true`**，会把产物发布出去 | npm README | 不小心就代用户发布了；必须显式关掉 |
| **额度/成本** | 创点计费、并发上限（1401）、套餐不足（1403/1404）、任务 1 小时超时 | SKILL 错误码表 | 6–12 条变体会排队；成本不可精细预估 |
| **创作控制** | 模板 ID 固定（一键成片默认 `978755842`，元素替换默认 `1028571394`）；参考视频 5–60s、≥480p、≤50MB、MP4/MOV；语言枚举有限 | npm README / SKILL | 你租的是它的模板和流水线，不是自己的能力 |

### 13.2 还有三个隐性坑

1. **版本漂移**：npm 包 2026-09-01 发 1.0.0，10-19 已到 1.3.0；而 skill 里把版本钉在 `1.0.x`。七周四个版本，接口与行为都可能变。
2. **商品解析有边界**：商品信息依赖抖店/抖音链接或商品 ID，失败码 `1422` 就是「服务端无法解析商品信息」。跨平台（淘宝/拼多多/独立站）不在覆盖内。
3. **能力比想象的多**：除了爆款裂变，还有 `submit_video_elements_replace_v2`（替换角色/商品/场景）和 `submit_marketing_task_v2`（一键成片）。这意味着 Kickart 的 B 不只是「换装」，而是「按模板重生成」——灵活度比 Ad+ 的本地 L1 高，但控制权在对方。

### 13.3 能怎么用（按可行性排序）

| 姿势 | 可行性 | 说明 |
|---|---|---|
| **内部 benchmark** | 高 | 用它跑 10 条，和自建比质量/成本，不进入产品 |
| **BYO 账号连接器** | 中高 | 用户在 Ad+ 里登录自己的 Kickart 账号，Ad+ 只做编排/对比/QA/交付；不碰 token 持久化 |
| **商业合作/白标** | 未知 | 需要商务确认转售、白标、SLA、结算；没谈成之前不能写进产品 |
| **当产品底座** | 低 | 许可、鉴权、数据、发布四道都过不去 |

### 13.4 上线前必须拿到的五个答案

1. LICENSE 是否允许「封装为第三方产品」和「转售/白标」？
2. 是否允许服务端持有用户 token（而不是每用户本机 OAuth）？
3. 素材保留多久？是否用于模型训练？能否签 DPA/保密协议？
4. 并发、QPS、日配额、SLA 是多少？超额怎么计费？
5. 产物版权/商用授权范围？是否带水印/品牌露出？

**结论：Kickart API 适合验证 B 的需求和做质量基线，不适合当产品底座。**

## 14. 只租视频模型、其余自建：可行吗

### 14.1 先修正前提

「仅基于视频模型」这句话在工程上不成立：A+B+商品库至少还需要五类能力，它们都不是写代码能写出来的。

| 能力 | 为什么绕不开 | 能否本地开源 |
|---|---|---|
| LLM（策划/脚本/卖点） | 分镜、hook、文案、卖点提炼 | 能（Qwen2.5 等，Apache-2.0），但本地 7B 质量弱于 API |
| TTS | 口播、旁白、多语言 | 能（CosyVoice，Apache-2.0） |
| ASR | 对齐字幕、参考片口播提取 | 能（Whisper，MIT） |
| 分割 | 商品/人物/服装 mask | 能（SAM2，Apache-2.0；rembg，MIT） |
| OCR | 标签保真、卖点识别 | 能（PaddleOCR，Apache-2.0） |

所以只有两种读法：

- **读法 A（可行）**：视频生成租 API，其余全部本地开源模型 + 自写代码；
- **读法 B（不可行）**：除了视频模型不碰任何模型——那 A 只能退化成「规则 + 模板幻灯片」，B 只能做剪辑拼接。

下面按读法 A 评估。

### 14.2 结论分数

| 判断 | 分数 | 说明 |
|---|---|---|
| 工程可行性 | **8/10** | 每个模块都有成熟开源件，难在集成与调优 |
| 「零外部依赖」 | **2/10** | 音乐、字体、视频模型、部分模型权重注定要买/租 |
| 观感对齐 Kickart | **4/10** | 卡在模板与音乐供给，不在代码 |
| 做出差异化产品 | **8/10** | 商品保真 + 本地私有 + 批量变体 + 成本透明 |
| 1–3 人 6 个月做出来 | **6/10** | 能出可用版，出不了「精修级」 |

### 14.3 模块清单：自建 / 租 / 买

| 模块 | 选择 | 许可 | 难度 | 质量上限 |
|---|---|---|---|---|
| Timeline + 渲染 | FFmpeg + Remotion + OTIO 风格 schema | FFmpeg LGPL/GPL；Remotion 商用收费 | 中 | 高（确定性） |
| 模板引擎 | 自写（槽位 + 约束 + JSON） | 自有 | 中 | 取决于设计供给 |
| 策划/脚本 | LLM API 或本地 Qwen | Apache-2.0 | 低 | API 高 / 本地中 |
| 商品板/抠图 | SAM2 + OpenCV + 合成回贴 | Apache-2.0 | 中高 | 高（可人工兜底） |
| 标签 OCR/QA | PaddleOCR + SSIM | Apache-2.0 | 中 | 高 |
| TTS | CosyVoice | Apache-2.0 | 中 | 高（需 GPU/慢） |
| ASR/字幕对齐 | Whisper | MIT | 低 | 高 |
| 口型 | LatentSync（替 Wav2Lip） | Apache-2.0 | 高（显存） | 中高 |
| 人脸一致性 QA | InsightFace | **仓库无 license，权重多限非商用** | 中 | 高但**不能直接用** |
| 变体/批次调度 | 自写 | 自有 | 中 | — |
| 音乐/音效 | 必须采购 | 商业授权 | 低 | 高 |
| 视频生成 | Seedance / Kling / MiniMax | 商业 API | 低 | 取决于模型 |

**结论：能自建的是「控制层」——timeline、模板引擎、商品真相、变体、QA、成本；必须租的是「生成层」；必须买的是「版权层」。**

### 14.4 五个真正难的地方（都不是写代码）

1. **模板与动效供给**：8–16 套能打的模板，是 1 设计师 + 1 动效 3–6 个月的工作量。没有它，A 就是「能生成但不高级」。
2. **音乐/字体授权**：短片的「专业感」一半来自声音。这块只能买，且要保留授权记录。
3. **视频模型的可控性**：5–10 秒片段、运镜/首尾帧/参考一致性都不由你定；失败重试照样计费。
4. **商品保真的长尾**：透明包装、反光、多件装、手部遮挡、异形——自动 90%，剩下 10% 必须有「人工补 mask / 回退原图」的兜底，否则一次翻车就失去信任。
5. **质量评估闭环**：没有 50–100 条 golden set + 盲评，你无法判断改动是变好还是变坏；这是团队最容易省、也最致命的一步。

### 14.5 许可证陷阱（「开源」不等于「可商用」）

| 组件 | 状态 | 处理 |
|---|---|---|
| Wav2Lip | 无 license，README 限研究/学术 | 换 LatentSync（Apache-2.0） |
| InsightFace | 仓库无 license；buffalo 等权重限非商用 | 只做内部评测，或换可商用的人脸模型 |
| MuseTalk | GitHub 标记 Other（NOASSERTION） | 商用前逐条核对 |
| Remotion | ≤3 人免费，超过收费；自动化 $0.01/次 | 计入成本 |
| FFmpeg | LGPL/GPL | 独立进程/动态链接，法务确认 |
| ComfyUI（若打包） | GPL-3.0 | 分发方式要谨慎 |
| FLUX.1 dev | 非商用 | 商用选 schnell/Apache 版本或换模型 |

### 14.6 六个月路线（1–2 人）

| 月 | 交付 | 验收 |
|---|---|---|
| M1 | Timeline + 渲染 + 1 套模板；商品图 → 6s 模板片 | 能出片，商品不变形 |
| M2 | 商品库（抠图/OCR/标签 QA）+ 模板 3 套 | 10 个真实 SKU 自动通过 ≥8 |
| M3 | 变体引擎 + 批次 + 成本预估；A 入口 | 一次出 6 条，单条成本可见 |
| M4 | B：参考片结构分析 + 本地换色/换字幕/换旁白 + 合成 | 6 条同结构变体，失败可补 |
| M5 | TTS/口播 + 质量门（身份/口型/安全区） | 口播片可交付 |
| M6 | 模板 8 套 + 音乐库 + 导出/交付包 | 盲评 ≥ 手剪基线 70% |

**验收底线**：单条成本、出片时间、失败率、盲评四项同时达标，才算「可行」；只看 demo 不算。

### 14.7 一句话

**可行，但要接受三个事实：视频模型只能租、音乐字体只能买、模板供给只能靠人。**
把工程力气花在「timeline + 商品真相 + 变体 + QA」这四件别人不愿做、也做不细的事上，比追 Kickart 的模板墙更现实。
